## 一、Day 5 · 检索基线（baseline）

报告：`eval/reports/retrieval_baseline_2026-10-11.md`

| 指标 | 值 | 说明 |
|---|---|---|
| Hit@5 | **0.5769** | 52 条有效样本（8 条越界不计分母） |
| MRR | **0.4427** | 第一名命中率一般，排序质量是短板 |
| 越界组平均 top1 分数 | 0.3266 | 8 条越界样本 |
| 正常组平均 top1 分数 | 0.4340 | 52 条正常样本 |

分类型：

| 类型 | 样本数 | Hit@5 | MRR |
|---|---|---|---|
| 简单事实 | 44 | 0.6136 | 0.4815 |
| 综合 | 8 | 0.3750 | 0.2292 |

### 三个结论

1. **综合类明显弱于简单事实类**（Hit@5 差 0.24）——因为答案分散在多个文档，
   而当前是"单次检索 top 5"，跨文档召回能力不足。这是 Day 7 优化的第一靶子。
2. **越界组分数只比正常组低 0.11**（0.3266 vs 0.4340），差距不够大
   → **"用相似度阈值拒答"这条路线在本语料上不可行**，必须依赖 grade 节点的语义判断
   （Day 4 的 CRAG 正好是这个设计）。这不是失败，是发现。

### 失败归因（人工填写，≥5 条）

| 问题 | 失败模式 | 归因 |
|---|---|---|
| 该教程涵盖哪些主要步骤？ | 问题质量问题 | 指代不明（"该教程"脱离上下文），LLM 自动出题的通病，应人工筛掉 |
| 片段中提到的复杂应用示例是什么？ | 问题质量问题 | 同上，问题离开了原片段就不可回答 |
| LangChain 推荐使用什么方式实现实时流式更新？ | 术语差异 | 问题用"实时流式更新"，文档用词是 "streaming modes"，主题相近文档（install）抢走了 top1 |
| 使用 agent 时如何实现结构化输出？ | 主题竞争 | 命中 04_agents.md 而非 09_structured-output.md，两者语义高度重叠，top5 里其实可能有正确答案但排序靠后 |
| 如果代理生成的 SQL 命令有错误会发生什么？ | 切分/噪声 | 答案在 sql-agent 文档的表格/代码块附近，被切分打散 |
| 中间件可以用于哪些场景？ | 术语差异 | "中间件"= middleware 的中文译法未在英文语料中出现，跨语言检索吃亏 |

**Top 2 失败模式**：① 自动问题质量差（指代不明）；② 中文提问 × 英文语料的术语不对齐。

## 二、Day 6 · 生成层评估（Ragas）

生成命令：`python -m eval.run_eval --limit 30 --note "baseline..."`
报告：`eval/reports/report_8d0adfd.md` / `.json`（30 条分层抽样，含全部 8 条越界题）

| 指标 | 值 |
|---|---|
| Hit@5 | 0.5769 |
| MRR | 0.4427 |
| Faithfulness | 0.8514 |
| Answer Relevancy | 0.7781 |
| Context Recall | 0.6458 |
| 越界拒答正确率 | 0.5000（4/8） |
| 平均延迟 | 18.16s（p95 35.69s） |

### 分析

1. **Faithfulness 0.85 说明系统大多数时候"按材料说话"**；剩余的 0.15 损失主要出现在
   检索资料本身不足时——生成节点带上了不相关片段仍尝试作答，此时 prompt 强约束会触发拒答
   （见拒答率），忠诚但无答案可用。
2. **拒答正确率 0.5（4/8）是最大改进点**：8 条越界题里有 4 条没有拒答。
   这直接引出 Day 7 的 E3 实验（强化 prompt v2 的拒答措辞），假设拒答正确率上升。
3. **平均延迟 18s 偏高**：CRAG 每个问题最多 4 次 LLM 调用（router/grade/rewrite/generate），
   其中 rewrite 触发时链最长。工程优化方向（本次未做）：router/grade 合并为一次调用、
   或直接用小模型做 router。

### 失败归因示例（3 条）

- 「公司内部的报销流程怎么走？」：模型未拒答，生成了一段通用报销建议
  → **生成层问题**：grade 误判 relevant（模糊问题检索到的空泛片段被判"沾边"），prompt v1 约束不够强；
- 「BAAI/bge-small-zh-v1.5 参数量？」：正确拒答
  → 检索组 top1 分数低 + grade 判 irrelevant + rewrite 后仍无 → 流程按设计工作；
- 「LangGraph 支持哪些编程语言 SDK？」：未拒答
  → 语料里出现过 "Python/JS SDK" 相关字眼，grade 判 relevant，
    模型据此扩写——**检索层给了"半相关"材料**，属于最难防的一类幻觉。

## 三、Day 7 · 对比实验

生成命令：`python -m eval.run_experiments --limit 30`
汇总报告：`eval/reports/experiments_summary.md`；逐题记录：`report_E1_chunk300_8d0adfd.json` / `report_E3_prompt_v2_8d0adfd.json`

| 指标 | baseline | E1_chunk300 | E3_prompt_v2 |
|---|---|---|---|
| Hit@5 | 0.5769 | 0.5577 | 0.5769 |
| MRR | 0.4427 | 0.3781 | 0.4427 |
| Faithfulness | 0.8514 | 0.697 | 0.5975 |
| Answer Relevancy | 0.7781 | 0.5583 | 0.5692 |
| Context Recall | 0.6458 | 0.4271 | 0.5625 |
| 越界拒答正确率 | 0.500 | 0.375 | 0.500 |
| 平均延迟(s) | 18.16 | 15.78 | 15.54 |

### E1（chunk 500→300）：假设不成立，不采纳

- 假设"简单事实 Hit@5 上升"**未验证**：持平 0.6136→0.6136；但 MRR 0.4815→0.4014 明显下降
  ——相关块仍在 top5，只是排名靠后了。机制：小块上下文少，embedding 区分度下降，top1 更难命中。
- 假设"综合类下降"**验证**：Hit@5 0.375→0.25。答案被切到更多块，跨块召回更吃亏。
- **与 Day 3 quick 实验（300 最优）结论相反**。Day 3 只有 10 题、只看 Hit@5，样本太小；
  本次 52 题检索评估 + 30 题端到端更可靠。**小样本实验结论不可信**，这本身是一个教训。

### E3（prompt v1→v2）：假设不成立，但发现了真正的瓶颈

- 拒答正确率持平 0.5→0.5。逐题归因发现：**8 条越界题中 5 条在 router 节点就被判
  `need_retrieval=False`，走"直接回答"分支**（如"公司内部报销流程""DeepSeek 训练数据规模"）。
  拒答机制只在检索路径生效（grade=irrelevant → refuse），router 短路完全绕过它。
  v2 强化的是检索路径的生成 prompt，对这 5 条题**根本不起作用**。
  → **拒答率的瓶颈在 router，不在生成措辞。** 这是本次实验最有价值的发现。
- 检索指标与 baseline 完全一致（Hit@5/MRR 逐分类相同），证明评估管线可复现。
- 但 context_recall 在**检索结果完全相同**的情况下仍从 0.6458 波动到 0.5625
  → LLM 裁判存在 ±0.08 量级的运行间噪声（有效样本 n≈22）。
  faithfulness 的 -0.25 超出噪声可解释范围，可能与 v2 措辞改变回答风格有关，
  但单次运行无法区分，需多次重复实验才能归因。**LLM-as-judge 指标必须跑多次取均值才可比较。**

### 后续优化方向（按优先级）

1. **router 加固**（针对拒答率 0.5）：router prompt 增加"凡涉及具体事实/数字/版本号一律检索"，
   或给 direct-answer 分支加拒答约束——直击 5/8 越界题的失效点；
2. **裁判方差控制**：Ragas 指标跑 3 次取均值，或换更稳定的裁判模型后再做 prompt 类消融；
3. 综合类检索（Hit@5 仅 0.375）：多查询改写 / HyDE / 增大 top_k 后重排。
